# PRD Context Schema

> 本文件定义 PHASE 0 中 产品需求 Agent 应从当前对话、Project / Workspace 以及可用项目资料中提取的信息结构。
>
> 该 Schema 用于帮助 Agent 判断“现有信息是否足以生成 PRD”，而不是检查完整工作流是否每个环节都存在。

# 1. Project Context

提取当前需求的基础上下文：

- 项目名称；
- 当前需求名称；
- 项目目标；
- 当前需求目标；
- 目标用户 / 使用角色；
- 当前业务场景；
- 已知业务约束；
- 已知时间、范围或资源限制；
- 当前 Workflow 阶段；
- 相关 人工审核 决策。

若某项不存在，不强制补齐。

---

# 2. Upstream Artifacts（均为可选）

完整工作流可能包括：

- 需求澄清；
- 洞察分析；
- MRD；
- 方案设计；
- 交互设计；
- 其他与本需求相关的项目资料。

## 规则

1. 上述 Artifact 均为可选，不要求齐全；
2. 实际项目可以跳过任意上游环节；
3. 不得因为某类 Artifact 缺失而默认阻断 PRD 生成；
4. 仅消费当前 Project 中实际存在且与本需求相关的资料；
5. 判断标准是“PRD 所需信息是否足够”，而不是“流程节点是否完整”；
6. 若缺失信息不影响 PRD 核心内容，则正常继续；
7. 若缺失信息会导致需求范围、核心规则、目标用户或关键交互无法确定，则在 PHASE 1 集中暴露；
8. 若涉及交互改动且缺少交互方案，则转交交互 Agent，不由 产品需求 Agent自行完成完整交互设计。

---

# 3. User-Specified Sources

记录用户在当前任务中明确指定的参考资料，例如：

- “以 MRD v2 为准”；
- “重点参考方案设计 v3”；
- “交互稿以最终评审通过版本为准”。

字段建议：

- source_name
- source_type
- version
- user_priority
- notes

用户明确指定的资料优先级高于自动发现的普通项目资料。

---

# 4. Confirmed Decisions

提取已被确认的业务决策：

- 已确认需求；
- 已确认目标用户；
- 已确认需求范围；
- 已确认方案；
- 已确认交互；
- 已确认实验设计；
- 已确认埋点需求；
- 人工审核 结论；
- 已明确排除的非目标。

对任何“尚未确认”的信息，不得放入 Confirmed Decisions。

---

# 5. Requirement Background

用于生成 PRD 第一章：

- 背景与现状；
- 当前问题；
- 用户痛点；
- 需求产生原因；
- 需求目标；
- 用户故事；
- 已知非目标。

用户故事用于说明：

> 谁需要什么，以及为什么需要。

推荐格式：

> 作为 [用户角色]，我希望 [完成某项目标或操作]，以便 [获得某种价值]。

用户故事属于需求背景，不作为需求详情的组织主线。

---

# 6. Requirement Value

用于生成 PRD 第二章。

## 6.1 定性价值

可包括：

- 用户价值；
- 业务价值；
- 效率价值；
- 体验价值；
- 运营价值；
- 风险降低价值。

## 6.2 定量价值

仅记录有可靠来源支持的数据：

- 当前 Baseline；
- 目标指标；
- 目标值；
- 目标提升幅度；
- 业务规模影响。

若没有可靠量化信息，不得自行生成数字。

---

# 7. Requirement Scope

用于生成 PRD 第三章。

按以下结构提取：

- 页面；
- 功能模块；
- 功能点概述；
- 涉及团队。

要求：

1. PRD 第四章所有实际开发需求都应映射回第三章中的某个功能点；
2. 已明确不在本期范围的内容应记录；
3. 若不同资料对范围描述不一致，记录为 Conflict。

---

# 8. Requirement Detail Context

用于生成 PRD 第四章。

组织方式：

> 页面 → 功能模块 → 功能点

每个功能点可提取：

- 功能说明；
- 前置条件；
- 业务规则；
- 用户操作；
- 系统响应；
- 交互方案引用；
- 已知状态；
- 已知异常；
- 已知边界；
- 已知验收标准；
- 依赖模块；
- 相关说明。

注意：

状态、异常与边界、GIVEN / WHEN / THEN 验收标准是否最终生成，由 PHASE 1 的用户选择决定。

---

# 9. Interaction Status

记录当前需求的交互状态：

- 是否涉及 UI / 交互改动：是 / 否 / 待确认；
- 是否已有交互 Artifact：是 / 否；
- 交互 Artifact 名称；
- 交互 Artifact 版本；
- 是否已 人工审核；
- 是否包含 ASCII Wireframe；
- 是否需要转交交互 Agent。

## 判断规则

### 已有交互方案

直接引用，不重复设计。

### 不涉及交互

不生成 UI 相关内容。

### 涉及交互但缺少交互方案

标记：

> interaction_required_but_missing = true

并转交交互 Agent。

---

# 10. AB Experiment Context

记录：

- 是否有 AB 实验需求：是 / 否 / 待确认；
- 实验目标；
- 核心指标：一个；
- 观测指标：多个；
- 空白对照组说明；
- 对照组说明；
- 实验组1；
- 实验组2；
- 实验组3（如有）；
- 实验周期（如已有资料）；
- 资料来源。

不得自行生成：

- 实验比例；
- 实验周期；
- 指标目标值；
- 未经确认的实验组方案。

---

# 11. Tracking Context

记录：

- 是否有埋点需求：是 / 否 / 待确认；
- 页面；
- 功能模块；
- 事件类型；
- 参数说明；
- 是否服务 AB 实验；
- 是否服务核心指标计算。

事件类型默认以：

- 曝光；
- 点击；

为主。

若用户或已有资料定义其他事件类型，可按实际资料补充。

---

# 12. Optional Detail Enhancements

记录 PHASE 1 中用户是否要求生成以下增强项：

- 状态说明：是 / 否；
- 异常与边界：是 / 否；
- GIVEN / WHEN / THEN 验收标准：是 / 否。

若 PHASE 1 尚未确认，则字段状态为：

> 待确认

---

# 13. Open Issues

所有不能可靠确定、且会影响 PRD 的信息都记录在此。

分类：

- Missing Information；
- Conflicts；
- Pending Decisions；
- Interaction Missing；
- Experiment Unclear；
- Tracking Unclear。

每条 Open Issue 至少记录：

- issue_id；
- priority：P0 / P1 / P2；
- affected_section；
- description；
- recommendation；
- source_conflict（如有）；
- status。

优先级：

- P0：阻塞需求开发、范围确定或核心方案落地；
- P1：不一定阻塞开发启动，但影响功能完整性、实验、数据或重要交互；
- P2：低风险细节，可后续确认。

---

# 14. Source Mapping

对关键 PRD 结论记录来源。

推荐结构：

| PRD 结论 | 来源 Artifact / 对话 | 版本 | 是否已确认 |
|---|---|---|---|

重点记录：

- 目标用户；
- 需求范围；
- 核心业务规则；
- 核心交互；
- AB 实验方案；
- 埋点方案；
- 量化目标。

Source Mapping 的作用是：

1. 避免 产品需求 Agent 无依据修改上游结论；
2. 发生冲突时快速定位来源；
3. 为 人工审核 提供依据；
4. 为后续评审 Agent 做一致性检查提供基础。

---

# 15. Completeness Judgment

PHASE 0 结束时，不检查“上游 Artifact 是否齐全”，而检查：

## 是否足以进入 PHASE 1

满足以下条件即可：

- 能说明当前需求大致背景；
- 能识别至少一个明确需求目标；
- 能形成初步需求范围；
- 能识别主要功能模块；
- 能判断是否涉及交互改动；
- 能识别当前仍存在的不确定项。

如果仍有缺失，但可以在提纲中集中确认，则可以进入 PHASE 1。

## 不足以进入 PHASE 1 的典型情况

例如：

- 完全无法判断用户想解决什么问题；
- 无法判断需求对象或范围；
- 已知涉及交互改动，但没有任何交互方案且该交互是需求核心；
- 不同来源对核心方案完全冲突，且无法判断最新确认结论。

这类情况应先请求必要补充或转交对应上游 Agent。
