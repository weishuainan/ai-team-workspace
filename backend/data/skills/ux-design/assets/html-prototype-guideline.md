# HTML 交互原型规范

> 本文件仅在 PHASE 2 判断为复杂需求、需要 HTML 交互原型时读取。
>
> HTML 原型的目标是“帮助用户体验和评审交互”，不是生产代码，也不是视觉成品。

# 1. 核心目标

HTML 原型必须做到：

- 可打开；
- 可点击；
- 主要 View 可进入；
- 关键交互可体验；
- 能准确反映上游已确认方案；
- 可以被 人工审核；
- 可以被截图脚本用于内部 Review。

---

# 2. 实现边界

## 应实现

- 页面 / View；
- 导航；
- Tab；
- Modal；
- Drawer；
- Panel；
- 表单；
- 列表；
- 卡片；
- 用户点击；
- 上游已确认的动态内容；
- 上游已确认的状态变化；
- 上游已确认的多步骤流程。

## 不应实现

- 真实生产接口；
- 真实账号 / 权限系统；
- 真实数据写入；
- 未确认业务能力；
- 未确认异常 / 失败 / 降级 / 重试流程；
- Icon 生成；
- 学城文档逻辑；
- 与交互评审无关的复杂工程化能力。

---

# 3. 文件组织

优先使用单文件 HTML：

```text
prototype.html
```

可内联：

- CSS；
- JavaScript；
- mock data。

原因：

- 易于预览；
- 易于归档；
- 易于分享；
- 不依赖学城 CSP；
- 不需要为了原型拆成生产级工程。

当单文件明显不利于维护时，可拆成：

```text
prototype.html
assets/
  app.js
  style.css
```

但不要无必要拆分。

---

# 4. 原型结构

HTML 应明确区分主要 View / 页面区域。

推荐给可切换 View 添加稳定标识：

```html
<section data-view="home" id="view-home">...</section>
<section data-view="detail" id="view-detail">...</section>
```

推荐给关键导航元素添加：

```html
<button data-view-target="home">...</button>
```

这样方便：

- 自动截图；
- 内部 Review；
- 定位主要页面。

---

# 5. Mock Data

所有内容使用 mock data。

要求：

- 数据要足以展示布局；
- 不使用真实敏感数据；
- 数据应符合上游业务含义；
- 不为了填满页面而发明新的业务字段；
- 可以使用“示例项目”“示例用户”“示例任务”等占位内容。

---

# 6. 交互设计

HTML 原型应优先实现最影响评审的交互：

- 进入页面；
- 导航 / Tab 切换；
- 展开 / 收起；
- Modal / Drawer 打开关闭；
- 表单操作；
- 关键按钮点击；
- 主要页面跳转；
- 上游已确认的状态变化；
- 上游已确认的动态生成过程。

不要为了“更真实”额外增加上游未定义场景。

---

# 7. 动效

动效属于 HTML 原型的一部分，不单独设 Phase。

适用：

- 内容逐步出现；
- Agent 工作过程；
- Panel 联动；
- 页面切换；
- 上游已确认的进度变化。

要求：

- 动效帮助理解，不炫技；
- 不改变业务逻辑；
- 可重复体验；
- 重新进入 View 时，必要时应能重置并重放；
- 避免只播放一次后无法复现。

---

# 8. 状态

只实现上游已明确状态。

例如上游定义：

```text
待执行 → 执行中 → 待人工确认 → 已完成
```

则 HTML 可实现这些状态切换。

若上游没有定义：

```text
失败
网络异常
重试
降级
```

则不要自行添加。

---

# 9. 视觉原则

视觉不是最终 UI 设计稿，但应满足：

- 层级清楚；
- 可读；
- 控件含义明确；
- 布局不明显错乱；
- 尽量参考当前产品 / Workspace 已有视觉规范；
- 若没有视觉规范，采用中性、简洁、低装饰的产品原型风格；
- 不生成品牌 Icon；
- 不把视觉风格本身当作交互创新点。

---

# 10. 可访问性与可用性

原型至少做到：

- 按钮文字可理解；
- 点击目标明显；
- 关键文本可读；
- 表单标签清晰；
- 不依赖纯颜色表达唯一含义；
- 页面在常见桌面窗口中不明显溢出。

若需求明确为移动端，应按移动端尺寸设计。

---

# 11. 内部 Review

HTML 生成后，使用：

```text
scripts/capture_prototype.py
```

对主要 View 截图。

截图仅用于内部 Review。

至少检查：

1. 页面是否正常渲染；
2. 主要 View 是否可进入；
3. 布局是否明显错位；
4. 文字是否明显溢出；
5. 关键模块是否缺失；
6. 关键按钮是否可操作；
7. 主流程是否符合上游方案；
8. 是否出现上游未定义的异常 / 失败 / 降级场景。

若发现问题：

> 先修改 HTML，再进入 人工审核。

---

# 12. 截图标识建议

为了便于脚本定位 View，可使用：

```html
<button data-view="home">首页</button>
<button data-view="detail">详情</button>
```

或：

```html
<a href="#home">首页</a>
```

或稳定的元素 ID：

```html
<button id="home">首页</button>
```

截图脚本会尝试按这些方式定位并切换视图。

---

# 13. 正式交付

复杂需求正式交付至少包括：

```text
design.md
prototype.html
```

其中：

`design.md`：

- 简要文字说明；
- 设计范围；
- 核心交互；
- 主要页面 / 区域；
- 设计依据；
- 必要的辅助图。

`prototype.html`：

- 可点击交互原型。

内部截图默认不作为正式用户交付物。
