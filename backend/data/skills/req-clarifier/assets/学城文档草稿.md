# req-clarifier — 需求澄清 Skill 说明文档

## 一、Skill 概述

req-clarifier 是为 AI 产运协作工作台（2026 Hackathon 项目）设计的「需求澄清」Agent Skill。它位于 Idea 提交后、需求洞察 Agent 分析前的预处理环节，核心职责是从用户提交的模糊需求描述中识别缺失的关键信息，生成结构化澄清卡片，帮助用户快速补全信息后流转至下游 Agent。

## 二、解决的问题

在产品运营协作中，需求提交者往往一句话描述想法，但接收方需要反复追问才能明确需求。这个 Skill 将这种隐性的、依赖经验的「追问能力」固化为标准化流程：

- 自动识别需求类型（功能开发、优化、Bug修复、活动策划、数据分析、策略制定、探索性想法）
- 按8个维度提取已有信息并检测缺口
- 动态生成最适合当前场景的澄清问题
- 为每个缺口提供推测默认值，降低用户回复成本

## 三、核心设计

### 3.1 八维度信息模型

Skill 定义了8个信息维度来评估需求的完整度：

| 维度 | 代码 | 含义 |
|------|------|------|
| 目标对象 | target | 针对什么产品/功能/用户群体 |
| 核心问题 | problem | 要解决什么问题 |
| 期望结果 | outcome | 希望达到什么效果 |
| 目标用户 | audience | 影响谁 |
| 优先级 | priority | 紧急程度 |
| 约束条件 | constraint | 有什么限制 |
| 成功指标 | metric | 怎么衡量成功 |
| 上下文背景 | context | 为什么现在提 |

### 3.2 需求类型与必填维度矩阵

不同类型的需求，必须具备的信息不同。Skill 维护了一个矩阵来确定哪些维度是必填的：

| 需求类型 | 必填维度 | 选填维度 |
|---------|---------|---------|
| feature_request（新功能） | target, problem, outcome | audience, constraint, metric |
| optimization（优化） | target, problem, outcome | metric, constraint, context |
| bug_fix（Bug修复） | target, problem | context, priority |
| activity_plan（活动策划） | target, outcome, audience | constraint, metric, priority |
| data_analysis（数据分析） | target, problem | metric, context, time_range |
| strategy（策略制定） | target, problem, outcome | audience, constraint, context |
| exploration（探索性想法） | target, problem | outcome, audience, context |

### 3.3 动态问题生成

问题数量不是固定的，而是根据缺口数量动态调整，平衡信息完整度和用户耐心：

- 0个缺口：不生成问题，直接判断"信息完整"
- 1-2个缺口：全部提问
- 3-4个缺口：最多4个，P0全问+P1选最重要的
- 5-6个缺口：最多5个，P0全问+P1选1个
- 7+个缺口：最多7个，P0+P1+P2各选

### 3.4 信息缺口三级分类

- P0 关键缺口：必填维度缺失，不补全无法进入下游 Agent
- P1 建议补充：选填维度缺失但影响较大
- P2 锦上添花：选填维度缺失且影响较小

## 四、输出格式：澄清卡片

Skill 输出标准化的 Markdown 澄清卡片，包含以下区块：

1. 需求类型识别（primary_type + 中文说明）
2. 信息完整度判断（完整/基本完整/不完整）
3. 需求摘要（一句话概括）
4. 已识别信息表格
5. 信息缺口分析（P0 + P1 分级）
6. 澄清问题列表
7. 建议默认值表格（含推测依据和确认方式）
8. 下一步建议（根据完整度推荐流转或补充）

## 五、工作流程

```
用户输入
  │
  ├─ Step 1: 解析输入，识别需求类型
  │
  ├─ Step 2: 提取已有信息（8维度）
  │
  ├─ Step 3: 检测信息缺口，按 P0/P1/P2 分级
  │
  ├─ Step 4: 动态生成澄清问题（数量视缺口而定）
  │
  ├─ Step 5: 生成建议默认值（含推测依据）
  │
  ├─ Step 6: 推荐下一步行动
  │
  └─ 输出澄清卡片
```

## 六、在 AI 产运协作工作台中的位置

```
Idea 提交 → [req-clarifier 需求澄清] → 需求洞察 Agent（洞察）→ Strategy Agent（策略）→ Decision Agent（决策）→ Execution Agent（执行）→ 质量评审 Agent（复盘）
```

req-clarifier 是整个 Agent 链路的入口守门人。它的价值在于：

- 保证进入下游 Agent 的需求具备最低信息完整度
- 降低 需求洞察 Agent 的信息处理负担
- 通过建议默认值机制减少用户回复成本，提升体验

## 七、边界处理

| 场景 | 处理方式 |
|------|---------|
| 输入过短（<10字） | 标注所有必填维度为P0，不强行猜测 |
| 输入过长（>500字） | 先提取摘要，按正常流程处理 |
| 包含多个需求 | 拆分为多张卡片，标注"需求1/N" |
| 包含结构化信息（如PRD片段） | 跳过已明确的维度 |
| 需求类型不明确 | 输出卡片标注"需求类型待明确" |

## 九、测试用例

| # | 场景 | 输入摘要 | 预期 |
|---|------|---------|------|
| 1 | 模糊功能需求 | "我们是不是可以加一个智能推荐功能" | 不完整，5个缺口，动态3-5问 |
| 2 | 完整活动策划 | "七夕大促神券活动，高频用户45-7，50万预算" | 基本完整，1-2个缺口 |
| 3 | 极短输入 | "首页转化率太低了" | 不完整，全维度缺口 |
| 4 | 探索性想法 | "竞品做AI客服，我们能不能也搞一个" | exploration类型，3-4问 |
| 5 | 多需求输入 | "优化注册流程+分析点击率+加签到功能" | 拆分为3张卡片 |
| 6 | 模糊Bug报告 | "搜索结果不太对" | bug_fix类型，4问以内 |
| 7 | 有上下文策略 | "三四线城市渗透率低，竞品补贴大，200万预算" | 基本完整，3问以内 |

## 十、迭代方向

- 增加与 需求洞察 Agent / Strategy Agent 的数据接口规范
- 支持用户历史需求模式学习（个性化默认值）
- 增加多语言输入支持
- 与 Human-in-the-loop 机制深度集成，支持渐进式补充
