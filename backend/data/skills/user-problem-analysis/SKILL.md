# 用户问题分析 Skill（user_problem_analysis）

## 1. 定位

在 AI 产运协作工作台中，由 需求洞察 Agent 在洞察分析阶段调用（材料总结确认后）。

材料总结（Skill 02）完成后，项目拥有了一份结构化的信息清单——事实、观点、用户问题、冲突点。但这只是"信息"而非"洞察"。本 Skill 的目标是：基于已确认的材料总结和需求澄清，从"信息"跨越到"洞察"，输出结构化的用户问题分析，明确用户画像、使用场景、核心痛点、问题原因（区分事实与假设），为 MRD 生成提供经过分析的问题定义。

产出类型为 `UserProblemAnalysis` 的 Artifact，经真人确认后进入 Shared Context。

## 2. 与其他 Skill 的关系

```
Skill 02 材料总结 → 输出：结构化信息摘要（已确认 Artifact）
Skill 01 需求澄清 → 输出：结构化需求（已确认 Artifact）
                        ↓
Skill 03 用户问题分析 ← 输入：材料总结 + 需求澄清 + 当前消息
                        ↓ 输出：用户问题洞察（Artifact）
Skill 04 MRD 生成 ← 输入：需求 + 洞察
```

## 3. 事实与假设框架

本 Skill 贯彻"事实≠判断≠假设"三层分离原则：

| 层级 | 定义 | 示例 | 归属字段 |
| --- | --- | --- | --- |
| **事实** | 有明确来源、可验证的客观信息 | 运营收到12条用户反馈；首单转化率从42%降至35% | `known_facts` |
| **判断** | 基于事实的合理推论，尚未被验证 | 选餐流程改版可能导致下单耗时增加，用户中途流失 | `cause_hypotheses`（hypothesis_type: judgment） |
| **假设** | 为解释现象提出的待验证因果假设 | 首页放置首单红包入口可能提升新用户转化 | `cause_hypotheses`（hypothesis_type: hypothesis） |

Agent 必须在 `cause_hypotheses` 的 `hypothesis_type` 字段中区分"判断"和"假设"，不可混为一谈。

## 4. 输入与输出

详细的输入 Schema、输出 Schema 和 Artifact 结构定义见 `assets/input-output-schema.md`。

### 输入摘要

| 来源 | 内容 | 必需性 |
| --- | --- | --- |
| 项目基本信息 | 项目名称、一句话描述、项目目标 | 必需 |
| 已确认需求澄清 | 结构化需求（目标用户、场景等） | 必需（若未执行则降级处理） |
| 已确认材料总结 | 核心事实、观点、用户问题、冲突点 | 必需 |
| 协作消息区 | 洞察阶段的补充讨论 | 可选 |
| 当前指令 | 用户 @Agent 的指令 | 必需 |

### 输出七大模块

1. **user_profiles**（用户画像）— 谁
2. **scenarios**（使用场景）— 在什么情况下
3. **pain_points**（用户痛点）— 遇到了什么
4. **known_facts**（已知事实）— 支持原因分析的客观数据
5. **cause_hypotheses**（原因假设）— 为什么会出现这些问题
6. **open_questions**（待验证问题）— 需要进一步验证的关键问题
7. **opportunities**（潜在机会点）— 可能的方向性机会

## 5. 执行规则

### 5.1 必须做的

1. **以材料总结为事实基础**。所有分析必须基于已确认的材料总结中的 `core_facts`。不得引入材料总结中不存在的新"事实"。
2. **严格三层分离**。每个原因假设必须明确标注为"判断"或"假设"：
   - **判断**：基于已知事实的合理推论。如"引导耗时增加导致用户流失"（有耗时数据和留存下降数据作为支撑）。
   - **假设**：提出的因果假设，尚缺乏直接证据。如"缩短流程能提高留存"（方向性推测，需要验证）。
3. **每条假设必须关联支撑事实**。`supporting_facts` 字段引用 `known_facts` 中的具体条目。没有事实支撑的假设不予输出。
4. **识别反面证据**。如果材料中存在与假设方向矛盾的信息，必须在 `contradicting_evidence` 中写出。
5. **提供验证方向**。每条假设和待验证问题都要给出具体的验证方式建议（如"对比新旧版本各步骤流失率""设计 A/B 测试"等），而非只说"待验证"。
6. **从材料总结的冲突点中提取分析线索**。冲突点往往指向问题的核心矛盾，必须将其纳入分析。
7. **分层定义用户**。不要笼统说"用户"，要细分到具体用户群体。如果材料只提到一类用户，就只定义一类，不臆造其他群体。
8. **场景化描述**。每个痛点必须关联到一个具体场景，描述用户的触发条件、期望结果和实际结果的差异。

### 5.2 禁止做的

1. **禁止编造事实**。只能引用材料总结中的已确认事实和当前阶段消息中的新信息。不得"合理补全"数据。
2. **禁止将假设表述为事实**。如"缩短流程能提高留存"是假设，不可以写成"缩短流程可以提高留存"。用词必须区分"可能""推测"与"确认"。
3. **禁止跳过验证方向**。每条假设和待验证问题都必须有 `verification_method` 或 `verification_suggestion`，不能只写"待验证"三个字。
4. **禁止越界输出方案**。本 Skill 输出"问题分析"和"机会点"，不输出"产品方案"或"功能设计"。方案是 Skill 05 的职责。
5. **禁止忽略冲突**。材料总结中的冲突点如果在分析中未被提及或解释，视为遗漏。
6. **禁止使机会点成为需求**。机会点是对"可能的方向"的轻量级识别，不等于"应该做什么"。不要把机会点写成功能需求。
7. **禁止引用被驳回的材料总结版本**。只基于 Shared Context 中 status 为 APPROVED 的材料总结。

### 5.3 信息不足时的处理

| 情况 | 处理方式 |
| --- | --- |
| 材料总结的 coverage 为"不足" | 正常执行，`analysis_confidence` 设为"低"，在 `open_questions` 中提示补充材料 |
| 材料总结中没有用户画像相关信息 | `user_profiles` 可为空或仅基于需求澄清中的目标用户，在 `open_questions` 中标注 |
| 材料总结的冲突点无法判断谁对谁错 | 不做判断，将冲突纳入原因假设的两面性分析，标注为待验证 |
| 无法从现有材料中提取任何原因假设 | 返回 `NEED_HUMAN`，提示"现有材料不足以支撑问题分析，建议补充用户行为数据或调研材料" |
| 需求澄清被跳过 | 正常执行，在 `open_questions` 中标注目标用户和场景信息可能不完整 |

### 5.4 假设编号与追溯规则

1. 每条假设分配唯一编号（H1, H2, H3...），在整个 Artifact 生命周期内不变。
2. 待验证问题通过 `related_hypothesis` 字段关联到假设编号，形成"事实 → 假设 → 验证"的完整追溯链。
3. 后续 MRD 和方案 Agent 可以通过假设编号引用本阶段的分析结论。
4. 若驳回后重新生成，假设编号重新从 H1 开始，但版本号递增。

### 5.5 分析优先级

当材料丰富、问题复杂时，按以下优先级组织分析：
1. 团队已达成共识的问题 > 存在分歧的问题
2. 有量化数据支撑的问题 > 仅定性描述的问题
3. 高频提及的问题 > 低频提及的问题
4. 影响核心链路的问题 > 边缘问题
5. 与项目目标直接相关的问题 > 间接相关的问题

## 6. 已知陷阱（Gotcha）

1. **"因果跳跃"陷阱**：事实"选餐流程改版后首单转化率下降"→假设"改版导致了转化率下降"。这只是一个假设，不是事实。必须标注为 hypothesis，还可能存在其他原因（如季节性波动、竞品活动等）。
2. **"单因归因"陷阱**：外卖转化率下降可能有多个原因（流程变长、优惠券体验差、配送时长增加等），不要只给出一个假设。至少考虑2-3个可能的原因。
3. **"验证空话"陷阱**：不要写"需要进一步分析"作为验证方式。要具体：对比什么数据（如新旧版本各步骤的流失率）、做什么实验（如 A/B 测试首页红包入口）、找谁确认（如找数据团队拉埋点）。
4. **"机会变需求"陷阱**：机会是"可能的方向"，不是"应该做什么"。不要写"应该在首页加首单红包弹窗"，应写"首页优惠前置可能降低首单流失"。
5. **"冲突回避"陷阱**：材料总结中运营说"用户找不到优惠券"，产品说"优惠券入口在结账页有显示"，不要回避矛盾。把矛盾纳入假设的反面证据或待验证问题。
6. **"过度自信"陷阱**：除非有充分的量化数据支撑，否则置信度不超过"medium"。宁可保守不可冒进。
7. **"忽视场景"陷阱**：不要只说"用户觉得下单复杂"，要说在什么场景下（首次点餐？选择商户时？结账时？）、做什么操作时觉得复杂。场景是痛点的上下文。
8. **"C端B端混淆"陷阱**：外卖场景下用户反馈（C端消费者：下单慢、找不到券）和商户反馈（B端商家：出餐慢、佣金高）是不同维度的问题，分析时不可混为一谈。
