# 材料总结 Skill（material_summary）

## 1. 定位

在 AI 产运协作工作台中，由 需求洞察 Agent 在需求澄清完成后、洞察分析阶段中调用。将项目中所有非结构化的讨论内容、用户反馈、业务背景等材料，整理为结构化的信息摘要，作为后续洞察分析和需求定义的事实基础。

产出类型为 `MaterialSummary` 的 Artifact，经真人确认后进入 Shared Context。

## 2. 与其他 Skill 的关系

```
Skill 01 需求澄清 → 结构化需求 + 待澄清问题
                        ↓
Skill 02 材料总结 ← 输入：项目内所有讨论、反馈、背景材料
                        ↓ 输出：结构化信息摘要（Artifact）
Skill 03 用户问题分析 ← 输入：材料总结结果 + 已确认需求
```

## 3. 输入与输出

详细的输入 Schema、输出 Schema 和 Artifact 结构定义见 `assets/input-output-schema.md`。

### 输入摘要

| 来源 | 内容 | 必需性 |
| --- | --- | --- |
| 项目基本信息 | 项目名称、一句话描述、项目目标、补充背景 | 必需 |
| 已确认需求澄清 | 结构化需求（目标用户、场景、问题等） | 可选 |
| 协作消息区 | 项目内所有消息（真人讨论、Agent 输出、系统消息） | 必需 |
| 用户反馈原始材料 | 消息区中用户粘贴的文本、补充背景字段 | 可选但有则必读 |

### 输出五大模块

1. **core_facts**（核心事实）— 有明确来源、可验证的客观信息
2. **key_viewpoints**（重要观点）— 团队成员的主观判断、推测或建议
3. **user_problems**（用户问题）— 从材料中提取的用户侧问题
4. **conflicts**（冲突点）— 材料中相互矛盾或存在分歧的信息
5. **open_questions**（待确认问题）— 材料中提及但信息不完整、需核实的事项

## 4. 执行规则

### 4.1 必须做的

1. **逐条阅读所有材料**，不跳过任何消息。每条消息至少判定是否包含有效信息。
2. **严格区分事实与判断**。事实归入 `core_facts`，判断归入 `key_viewpoints`，绝对不可混放。
   - 事实：有明确来源、可验证。如"运营收到12条用户反馈""7日留存从42%降至35%"。
   - 判断：基于事实的主观推论。如"新手流程可能存在理解成本""留存下降可能与引导变长有关"。
3. **保留来源标注**。每条事实和观点必须标注来源（发送者 + 消息类型），便于后续追溯。
4. **识别冲突**。不同材料对同一事项给出矛盾信息时，必须提取为冲突点，而非自行选择一个。
5. **提取待确认问题**。材料中提及但信息不完整、需要进一步核实的事项，列入 `open_questions`。
6. **按信息原意归类**，不添加材料中不存在的信息，不"合理推测"后当作事实输出。

### 4.2 禁止做的

1. **禁止编造数据或事实**。材料说"留存有所下降"但没给具体数字，不得编造"留存下降15%"。输出应为"留存有所下降（具体幅度未知）"。
2. **禁止合并不同来源的信息后模糊出处**。如"运营说留存42%，数据系统显示35%"，应分别列出并标注来源不同。
3. **禁止将观点包装为事实**。如"缩短流程可能提高留存"是假设，不是事实。
4. **禁止省略冲突点**。冲突点是后续分析的关键输入，不得为了"看起来更整洁"而隐藏矛盾。
5. **禁止对材料做评价或建议**。本 Skill 只做"整理"不做"分析"，不输出"建议"或"方案"。分析与建议是 Skill 03 的职责。
6. **禁止引用被驳回的历史版本**。只处理当前 Shared Context 中已确认的内容和当前阶段的消息。

### 4.3 信息不足时的处理

| 情况 | 处理方式 |
| --- | --- |
| messages 为空 | 返回 `NEED_HUMAN`，提示补充材料 |
| 材料总量极少（<100字） | 正常执行，在 `open_questions` 中标注材料不足 |
| 材料全是闲聊/无关内容 | 正常执行，`core_facts` 可能为空，`coverage_assessment` 标注"不足" |
| 材料中存在大量重复信息 | 去重后保留一条，在 `source_count` 中记录原始条目数 |
| 材料中包含明显错误信息 | 不纠正，按原意提取，但在 `open_questions` 中标注"该信息可能有误，建议核实" |

### 4.4 去重与合并规则

1. 合并为一条事实，在 `source` 字段中列出所有来源。
2. 若同一信息被多次提及，在 `frequency_mention` 中反映频次。
3. 不同人表达相同观点时，在 `holder` 中列出所有持有人，`is_consensus` 标记为 `true`。

### 4.5 优先级规则

当材料量很大时（>50条消息），按以下优先级处理：
1. 包含具体数据/数字的消息 > 感性描述
2. 用户反馈原文 > 转述
3. 业务目标相关 > 旁支信息
4. 近期消息 > 早期消息（但早期消息中的事实仍需提取）

## 5. 已知陷阱（Gotcha）

1. **"合理推测"陷阱**：用户说"下单太慢了"，不要输出"下单太慢了，因为页面加载时间长"。后半句是你的推测。
2. **"数字幻觉"陷阱**：材料说"很多用户投诉配送慢"，不要输出"73%的用户投诉配送慢"。你没这个数据。
3. **"冲突隐藏"陷阱**：商户说佣金高，运营说佣金已降低，不要只保留一方。必须记为冲突。
4. **"过度合并"陷阱**：三条反馈分别提到配送慢、找不到优惠券、支付失败，不要合并为"用户有多个问题"。应分别列出。
5. **"角色混淆"陷阱**：运营转述的用户反馈，来源标注为"运营-XX（转述用户反馈）"，不能直接标为"用户反馈"。
6. **"C端B端混淆"陷阱**：外卖场景下，用户反馈（C端消费者）和商户反馈（B端商家）必须区分标注，source_type 分别为 `user_feedback` 和 `merchant_feedback`。

## 6. 输出格式

严格按照以下 JSON Schema 输出，不输出任何 JSON 之外的内容：

```json
{
  "summary_scope": "本次总结覆盖的材料范围",
  "source_count": 0,
  "material_types": ["用户反馈", "讨论记录"],
  "core_facts": [
    {
      "fact": "事实描述",
      "source": "来源标注",
      "source_type": "user_feedback",
      "confidence": "high"
    }
  ],
  "key_viewpoints": [
    {
      "viewpoint": "观点内容",
      "holder": "持有人",
      "reasoning": "依据",
      "is_consensus": false
    }
  ],
  "user_problems": [
    {
      "problem_description": "问题描述",
      "user_segment": "用户群体",
      "severity": "high",
      "frequency_mention": "frequent",
      "source": "来源"
    }
  ],
  "conflicts": [
    {
      "conflict_description": "冲突描述",
      "position_a": "观点A",
      "position_a_source": "A来源",
      "position_b": "观点B",
      "position_b_source": "B来源",
      "resolution_status": "unresolved"
    }
  ],
  "open_questions": [
    "待确认问题1",
    "待确认问题2"
  ],
  "coverage_assessment": "充分|一般|不足",
  "confidence_level": "高|中|低"
}
```

### 字段说明

- `source_type`：`user_feedback`（用户反馈/评价）/ `merchant_feedback`（商户反馈）/ `discussion` / `business_data` / `background` / `historical_doc`
- `confidence`：`high`（有明确数据支撑或多人确认）/ `medium`（单一来源但信息明确）/ `low`（信息模糊或来源不确定）
- `severity`：`high` / `medium` / `low` / `unknown`
- `frequency_mention`：`frequent` / `occasional` / `single`
